# Stage 3 Scoring Rubric — Plutchik 8-Dim from Bilibili Danmaku

> **Audience:** 你（AI Agent，正在一次对话里驱动 emoekg）。Stage 2 产出了
> `chunks.md`，此刻你的工作是通读它，按下表把每个 chunk 打成 8 维 0–10 分，
> 然后把全部结果以 JSON 列表形式写回 `scores.json`。

---

## 1. 你要产出什么

一个 JSON 文件（`scores.json`），**数组长度必须等于 `chunks.md` 里的 chunk 数**。
每一项结构如下：

```json
{
  "chunk_id":     "C001",
  "time_start":   0,
  "time_end":     15,
  "n_danmaku":    42,
  "joy":          7,
  "trust":        2,
  "fear":         0,
  "surprise":     4,
  "sadness":      0,
  "disgust":      0,
  "anger":        0,
  "anticipation": 8,
  "note":         "全场在刷哈哈哈 + 蹲下一集"
}
```

字段说明：

| 字段 | 必填 | 说明 |
|---|---|---|
| `chunk_id` / `time_start` / `time_end` / `n_danmaku` | ✅ | 原样抄 `chunks.md` header |
| 8 个情绪维度 | ✅ | 整数 **0–10**，缺一不可，不能给小数 / 负数 / >10 |
| `note` | ✅ | ≤30 字，中文，概括本 chunk 最主导的情绪场面；SPARSE 块写 `"SPARSE"` |

---

## 2. 打分标尺（必须记住的 4 个分数锚点）

| 分数 | 含义 | 行为判据 |
|---|---|---|
| **0** | 完全没有此情绪 | 该维度的表达在本 chunk **一条都没有** |
| **3** | 微弱 / 背景 | 有 1–2 条相关表达，但不是主流 |
| **6** | 明显 / 被感知 | 多条相关表达，接收者能**一眼辨认出**这个情绪 |
| **9** | 刷屏 / 支配 | 该维度**占本 chunk 半数以上弹幕**或出现了强刺激词汇高频重复 |

> 7、8、10 是"边界分"。**10 留给真的刷屏到离谱**的情况（全屏 233、全屏哈哈、
> 全屏卧槽），不要轻易给。同理 1、2 留给"比 0 多一丝但远没到 3"。

---

## 3. 八个维度的弹幕识别指南

这些不是"硬关键词列表"——弹幕充满谐音、emoji、表情包语义，你需要**理解上下文**。
下表给的是 **原型信号** 和 **边界警示**。

### 3.1 joy（喜悦 / 快乐 / 欢乐）
- ✅ 原型：`哈哈哈`、`233`、`笑死`、`太乐了`、`好活`、`笑不活`、笑哭 emoji
- ⚠️ 边界：`笑死` 如果上下文是嘲讽/愤怒，算 anger 或 disgust，不算 joy
- ⚠️ 边界：`哈哈` 只有 1 个字母/字符的短促笑声 ≠ 刷屏笑

### 3.2 trust（信任 / 认可 / 赞同）
- ✅ 原型：`yyds`、`稳`、`信了`、`专业`、`靠谱`、`权威`、`大佬`、`说得对`
- ⚠️ 区分于 joy：trust 是"我信你 / 你牛"，joy 是"哈哈这个好笑"
- ⚠️ 夸奖主播的声音/颜值走 joy（愉悦），夸主播的**判断/技术**走 trust

### 3.3 fear（恐惧 / 担忧 / 紧张）
- ✅ 原型：`要出事了`、`慌`、`完蛋`、`害怕`、`瑟瑟发抖`、`不敢看`、`心悬`
- ⚠️ 解谜/恐怖场景出现"别进去"、"退后"等警告语，算 fear
- ⚠️ 对**未来可能有坏事**的担忧是 fear；对**正在发生的坏事**的难过是 sadness

### 3.4 surprise（惊讶 / 错愕 / 意外）
- ✅ 原型：`卧槽`、`啊这`、`???`、`离谱`、`什么情况`、`震惊`、`离大谱`、`?.`
- ⚠️ `卧槽` 如果是骂人情境走 anger；是赞叹的 `卧槽牛逼` 走 trust/joy
- ⚠️ **多个问号 `?????`** 通常是 surprise 而不是疑问

### 3.5 sadness（悲伤 / 心疼 / 破防）
- ✅ 原型：`破防了`、`emo`、`难过`、`泪目`、`心疼`、`哭了`、`好惨`、`唉`
- ⚠️ `哭了` 也可能是"笑哭"（joy 10）——看上下文和 emoji

### 3.6 disgust（厌恶 / 反感 / 下头）
- ✅ 原型：`恶心`、`下头`、`辣眼`、`反胃`、`呕`、`作呕`、`看不下去`
- ⚠️ disgust 的核心是"想躲开"，anger 的核心是"想攻击"。下头是 disgust，骂人是 anger

### 3.7 anger（愤怒 / 咒骂 / 敌意）
- ✅ 原型：`退游`、`策划死`、`辣鸡`、`垃圾`、`滚`、`气死`、脏话、`草`（愤怒语气）
- ⚠️ 区分于 disgust：anger 指向**对象**（骂某人/某游戏/某公司），disgust 指向**感受**
- ⚠️ `草` 如果是惊讶语气（`草？`）走 surprise，不走 anger

### 3.8 anticipation（期待 / 催更 / 蹲）
- ✅ 原型：`蹲下一集`、`催更`、`快更新`、`期待`、`坐等`、`求出`、`等你`
- ⚠️ 区分于 trust：anticipation 是"对未来的期盼"，trust 是"对当下判断的认可"
- ⚠️ 视频**结尾附近**的 anticipation 往往更高（观众渴望续集）

## 4. 特殊规则

### 4.1 SPARSE 规则（必须遵守）
如果 chunk header 里出现 **`【SPARSE】`** 标记，或 `n_danmaku < 3`：

* **8 个维度全部打 0**
* `note` 字段写 **`"SPARSE"`**（就这 6 个字符）
* 不要强行"发挥想象"给它打分——数据不足就是不足

### 4.2 多情绪共存
真实弹幕经常 joy + surprise + anticipation 同时高分（比如一个精彩 combo 镜头），
这是正常的，不要为了"区分度"人为压低某一维。**8 个维度独立评分，不是此消彼长。**

### 4.3 复读 / 梗 / 表情包
* 复读同一条弹幕**算倍数**（100 条 `哈哈` 比 5 条 `哈哈` 的 joy 强）
* 单独的表情/emoji 按**它最常用的情绪**计数（😂→joy、😱→surprise、🤮→disgust）
* 识别不出的梗**按它明显的正/负向基调归入对应维度**；拿不准就给 2–4 分，别给 0 也别给 9

### 4.4 `note` 字段写作
* ≤30 个中文字
* 概括本 chunk **最主导的情绪场面**，如：`大量233刷屏 + 催下一集`
* 不要写你的打分理由、不要写算法分析、不要写"该区间弹幕分布较为均匀"
* SPARSE 块就写 `"SPARSE"`

## 5. 完成后的自检清单

在把 `scores.json` 写回磁盘**之前**，确认：

- [ ] 数组长度 = `chunks.md` header 里写的 chunk 总数
- [ ] 每一项都有 8 个情绪 + `chunk_id` + `time_start` + `time_end` + `n_danmaku` + `note` 共 13 个字段
- [ ] 每个情绪值都是 `int` 且 ∈ [0, 10]
- [ ] `chunk_id` 严格按 `C001`、`C002`、… 顺序递增
- [ ] SPARSE 块都是 `[0]*8` + `note="SPARSE"`
- [ ] 非 SPARSE 块**至少有一个维度 ≥ 3**（如果全 0，说明你漏看了）

然后继续做 §6。

## 6. 产出 Executive Summary (`insights.json`)

> **新协议（v0.1.1 起）：** 打完分之后、跑 `emoekg finalize` 之前，你还要把
> 研究洞察写回 `insights.json`——这是报告 Hero 区的 TL;DR，是整份报告里
> 唯一"**给人看的**"的话术。研究员打开报告第一眼就看它。

### 6.1 你要产出什么

一个 JSON 文件（`insights.json`），结构：

```json
{
  "summary": "观众的情绪曲线呈现『期待—识别共鸣—信任背书』的三段式演变。",
  "insights": [
    {
      "title": "期待先行",
      "body":  "00:30 价格公布瞬间 anticipation 飙到 7，早于任何内容讲解。"
    },
    {
      "title": "跨 IP 识别共鸣",
      "body":  "09:15 电锯人/只狼架势条识别引发 joy 峰值 7——笑点来自玩家自发的模组识别，不来自 UP 的介绍。"
    },
    {
      "title": "同侪背书 > 作者背书",
      "body":  "trust 两个峰值都来自弹幕互相 confirm『不卡』，而不是 UP 本人夸奖。"
    }
  ]
}
```

### 6.2 字段规范

| 字段 | 必填 | 规范 |
|---|---|---|
| `summary` | ✅ | **一句话**（30–80 个中文字），概括整个视频的情绪核心，**必须是洞察性语言**，不是机械描述 |
| `insights` | ✅ | 恰好 **3 条**。多了报告放不下，少了就是偷懒 |
| `insights[].title` | ✅ | **4–8 个中文字**，像报刊小标题（「期待先行」「梗即共振」），不是描述性短语 |
| `insights[].body` | ✅ | **1 句 40–80 字**。给出**时间点 + 数据证据 + 为什么重要** |

### 6.3 好 summary vs 坏 summary 对照

| ❌ 坏 | ✅ 好 |
|---|---|
| 「这个视频获得了很多正面评价。」（空话） | 「观众在梗识别瞬间爆发，在作者口播时反而冷场。」（有张力） |
| 「joy 和 trust 是主导维度。」（算法腔） | 「观众的信任不来自作者，来自弹幕互相背书。」（洞察） |
| 「视频时长 15:14，弹幕 221 条。」（元数据） | 「十五分钟里只有三个真正的情绪炸点——全部发生在玩家自己接梗的瞬间。」（诠释） |

### 6.4 好 insight body vs 坏 insight body 对照

| ❌ 坏 | ✅ 好 |
|---|---|
| 「joy 维度在 09:15 处较高。」 | 「09:15 电锯人梗识别引发 joy=7，刷屏『电次不要开门』『这不电锯人吗』。」 |
| 「anticipation 是主要情绪之一。」 | 「价格公布的 00:30 anticipation 直接 7 分，观众『已取餐』『拿下了』秒转化。」 |
| 「有些弹幕表达了不满。」 | 「11:30 trust 跌到 2——技术抬杠『这是哪个游戏？哦对是我的世界』打断了推荐节奏。」 |

### 6.5 三条 insight 怎么选

想象你在给**一个 UX 研究员做 elevator pitch**——他只有 60 秒，你**必须**让他带走三件事：
1. **节奏洞察**：情绪高峰/低谷何时出现？有什么规律？
2. **机制洞察**：情绪被什么**触发**？作者、内容、弹幕、梗、画面？
3. **反差洞察**：有什么出乎意料？哪里的数据和直觉相反？

如果三条都是「joy 在 xx 高 / trust 在 yy 高」这种**罗列**，你就失败了。
研究员已经看得到图表，他要的是**解读**。

### 6.6 `insights.json` 自检清单

- [ ] `summary` ≥ 30 字 ≤ 80 字，是"洞察"不是"描述"
- [ ] `insights` 数组长度严格 = 3
- [ ] 每条 `title` 4–8 个字，像报刊小标题
- [ ] 每条 `body` 40–80 字，包含**时间点 + 证据 + 意义**
- [ ] 三条 insight 覆盖"节奏 + 机制 + 反差"三种视角，不要三条都讲同一件事

### 6.7 完成后

```
1. 写好 scores.json     ← Step 3 打分
2. 写好 insights.json   ← Step 6 洞察
3. 运行 emoekg finalize -o <working_dir>
4. 检查 emoekg_report.html 的 Hero 区是否包含你的 TL;DR + 三条 insight
```

如果 Hero 区没出现——大概率是 `insights.json` 结构错了（`summary` 为空或 JSON 解析失败）。
回去检查 §6.2。
